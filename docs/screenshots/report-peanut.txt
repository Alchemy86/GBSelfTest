--- TIM: the divider and the timer
GB-TIM-01 ok   the divider and the timer share one counter
GB-TIM-02 ok   writing DIV clears it

GB-TIM-04 ok   TAC bit 2 stops the timer

GB-TIM-06 FAIL writing DIV can itself clock the timer
      got $0000  want $0001
      -> clearing the divider while the timer's watched bit was set did not increment TIMA. The timer counts falling edges of one bit of the divider's own counter, and a write that clears that bit IS a falling edge
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-tim-06
GB-TIM-07 FAIL switching the timer off can clock it once more
      got $0000  want $0001
      -> clearing the enable bit while the timer's watched bit was set did not increment TIMA. What is counted is the falling edge of the watched bit ANDed with the enable, so switching the enable off is itself a falling edge
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-tim-07
--- INT: interrupts
GB-INT-01 ok   IF's top three bits read as one
GB-INT-02 FAIL EI is delayed and DI cancels it
      -> an interrupt was serviced between EI and the instruction after it. EI sets a latch that only reaches the master enable one instruction later, and a DI landing in that window clears it again
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-int-02
GB-INT-03 ok   EI then NOP does take the interrupt
GB-INT-04 ok   the lowest vector wins
GB-INT-05 FAIL HALT with IME clear and a pending interrupt
      got $0001  want $0002
      -> the byte after HALT ran once, not twice. When HALT is reached with interrupts disabled and one already pending, the fetch that follows does not advance the program counter
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-int-05
GB-INT-06 ok   HALT wakes without servicing when IME is clear
GB-INT-07 FAIL dispatch costs five machine cycles
      got $005B  want $0030
      -> taking an interrupt is five machine cycles: two idle, the high half of the program counter pushed, the low half pushed, then the vector fetched. A flat sixteen or twenty T-cycles applied in one lump does not measure the same
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-int-07

--- PPU: timing and the rendering fingerprint
GB-PPU-01 FAIL a frame is 70224 cycles, measured against DIV
      got $0119  want $0112
      -> the divider and the display disagree about how long a frame is. A frame is 154 lines of 456 cycles, which is 70224 cycles, which is 274.3 divider increments
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-01
GB-PPU-02 ok   a scanline is 456 cycles
GB-PPU-03 ok   LY counts 0 to 153 and wraps
GB-PPU-04 ok   STAT reports mode 2, then 3, then 0
GB-PPU-05 ok   the LY equals LYC flag and its interrupt
GB-PPU-06 ok   mode 3 is 172 cycles with nothing to draw
GB-PPU-07 FAIL fine scrolling lengthens mode 3
      got $0000  want $0001
      -> an SCX of 4 must make mode 3 four cycles longer: the first four pixels of the leftmost tile are fetched and thrown away. A mode 3 of fixed length cannot show this
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-07
GB-PPU-08 FAIL objects on a line lengthen mode 3
      got $0000  want $000F
      -> ten objects on a line did not lengthen mode 3. Each one stops the background fetcher for at least six cycles while its own row is fetched; a renderer that draws the line in one go and charges a fixed 172 cycles reports no penalty at all
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-08
GB-PPU-09 FAIL the window lengthens mode 3
      got $0000  want $0002
      -> starting the window did not lengthen mode 3. Taking it over costs at least six cycles: the fetcher throws away what it had and begins again from the window's own map
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-09
GB-PPU-10 FAIL VRAM is unreadable during mode 3
      got $0000  want $00FF
      -> the CPU read real data out of video RAM while the fetcher owned the bus. During mode 3 a read must return $FF; a game that writes there mid-line is relying on it being ignored
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-10
GB-PPU-11 FAIL OAM is unreadable during modes 2 and 3
      got $0012  want $00FF
      -> the CPU read object memory while the PPU was scanning it. During modes 2 and 3 a read must return $FF, which is why every game copies its objects in during the blank
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-11
GB-PPU-12 ok   only ten objects are drawn per line
GB-PPU-13 ok   objects switched off in LCDC cost nothing
GB-PPU-14 ok   the LCD off means LY 0 and mode 0
GB-PPU-15 ok   the STAT interrupt is one line, not four
GB-PPU-16 FAIL writing STAT raises a spurious interrupt
      got $0000  want $0002
      -> writing STAT with no condition selected did not raise the interrupt. On this machine the write acts for one cycle as though every condition were selected, and games depend on it
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-16
GB-PPU-17 ok   a window past the right edge costs nothing
GB-PPU-18 FAIL an object off the left edge still costs
      got $0000  want $000C
      -> ten objects placed entirely off the left of the screen cost the fetcher nothing. They are still found by the scan and their rows are still fetched; only the drawing is thrown away
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-18
GB-PPU-19 ok   vertical scrolling costs the fetcher nothing
GB-PPU-20 FAIL a VRAM write during mode 3 is dropped
      got $005A  want $0000
      -> a byte written into video RAM during mode 3 was still there afterwards. The fetcher owns that bus while it is drawing and a write there never reaches the memory, which is what lets a game write blindly and only lose the writes it placed badly
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-20
GB-PPU-21 FAIL an OAM write during the scan is dropped
      got $005A  want $0000
      -> a byte written into object memory during the object scan was still there afterwards. The PPU owns that bus through modes 2 and 3, which is why every game copies its objects in during the blank instead
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-21
GB-PPU-22 FAIL object memory corrupts, or does not, per console
      got $0000  want $0001
      -> not one byte of object memory changed. On this console the increment unit's operand reaches the bus the object scan is using, and a sixteen-bit increment through $FE00-$FEFF during mode 2 corrupts a row of it. Hooking the read and the write paths and stopping there is the usual way to miss this: no read and no write is involved
      -> https://github.com/Alchemy86/TerminalGB/blob/main/docs/gbselftest.md#gb-ppu-22

--- coverage
This cartridge tests the machine from the inside. That bounds what it
can see, and the bounds are these:

NOT TESTED, and not testable from a cartridge:
  * the composited picture. There is no framebuffer to read: the PPU
    streams pixels to the panel and keeps none of them. Pixel accuracy
    needs a host holding a reference image -- use the Mealybug Tearoom
    tests for that. What IS tested here is the rendering FINGERPRINT:
    mode 3 gets longer when the fetcher has more work to do, and that
    is measurable from inside to a resolution of four dots.
  * anything finer than four dots. The CPU can only observe on machine
    cycle boundaries, so a one, two or three dot difference -- an SCX of
    1, 2 or 3 for instance -- is below the floor for any cartridge.
  * the four-dot window at the top of the last scanline, where LY
    reads 153 before reading 0. It is below the resolution above, so
    GB-PPU-03 accepts either reading and says so.
  * sound as sound. Register behaviour and the length counter are
    checked; what comes out of the speaker is not.
  * the boot ROM itself, which has already finished.
  * other consoles. Every run reports which machine it thinks it is on
    and skips what does not apply, rather than guessing.
  * which VRAM source a double-speed PPU write commits to. GB-CYC-09
    and GB-PPU-07 check that double speed switches at all and that the
    PPU's dot clock does not speed up with the CPU, but a commit-timing
    bug that only changes which tile a dot samples is a pixel, and no
    cartridge can read one. See docs/double-speed.md.
